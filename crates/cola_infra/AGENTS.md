# 项目编码约束

本文件约束本仓库后续新增和修改的代码、配置、文档及计划文件。若子目录存在更具体的 `AGENTS.md`，应同时遵守；发生冲突时优先遵守更具体且不违反本文件安全要求的约束。

## 1. 文件头格式

每个新增文件的第一行必须说明**仓库相对文件位置**和简短摘要；第二行必须记录创建日期。示例：

```text
// server/src/transport/ws.rs -- WebSocket transport adapter
// 2026/10/7 13:38 Created.
```

文件头要求：

- 路径使用仓库根目录相对路径，不使用本机绝对路径；示例路径中的文件名/目录必须与实际位置一致。
- 时间格式为 `YYYY/M/D HH:mm Created.`，采用项目所在地/开发环境的本地时间；创建时记录真实创建时间，不得复制示例时间冒充实际时间。
- 修改已有文件时保留原有创建时间，不得把修改时间伪装成创建时间；如果旧文件缺少本规范文件头，在本次确需修改该文件时再补齐，并尽量从 Git 历史确认原创建日期，无法确认时明确使用可验证的初次纳入日期或在变更说明中注明。
- 文件头必须是文件的实际第一行和第二行；不得在它们之前放 BOM 以外的注释、空行、shebang、版权声明或 Markdown 标题。若语言要求 shebang 必须为第一行，先说明冲突并采用该语言/工具链允许的方案。
- 注释语法必须符合文件格式，保持这两行仍为可识别注释，不得破坏解析或渲染。

常见文件类型示例：

```rust
// server/src/main.rs -- Server process entry point
// 2026/10/7 13:38 Created.
```

```toml
# server/Cargo.toml -- Server crate manifest
# 2026/10/7 13:38 Created.
```

```jsonc
// config/example.json -- Example service configuration
// 2026/10/7 13:38 Created.
```

```markdown
<!-- /PLAN/PLAN-YYYY-MM-DD-HHMMSS-title.md -- Architecture plan -->
<!-- YYYY/M/D HH:mm Created. -->
```

对于不支持注释或对文件头有强制语法要求的格式（例如严格 JSON、部分生成文件、脚本 shebang），不得添加会导致文件无效的内容；应先确认该格式可接受的元数据位置，或在对应目录的文档中登记例外。

## 2. 传输层与业务逻辑

- WS 与 WT 必须作为独立 Transport Adapter 实现协议连接、帧/流收发、关闭和错误转换。
- 共享 Handler、业务用例、连接注册表和房间逻辑不得依赖 Actix WebSocket Context/Actor 地址或 WebTransport 专有类型。
- 新传输层只调用公共连接/消息接口；传输适配器不得复制业务路由、授权或房间广播逻辑。
- WT 指 WebTransport；WT 使用 `wtransport` 的选型需先验证 Rust/Tokio 兼容性、TLS、HTTP/3 和 UDP 部署条件。不可把 WebTransport 当成普通 WS 路由。
- 客户端负责 WT 优先及建连失败后 WS 重连。服务端不得声称可将未建立的 WT 会话原地转换为 WS。
- 慢连接发送队列必须有界，并显式定义队列满的限流/断开策略；不可采用无界队列掩盖背压。

## 3. 消息格式

- 当前传输消息格式为 JSON，必须通过独立 Codec 与内部消息模型转换。
- 业务 Handler 不直接解析 JSON 字符串或构造协议帧。
- protobuf 是后续扩展；未完成实现、协商及测试前，不得宣称 protobuf 已受支持。
- 对外协议变更需考虑版本兼容、输入大小上限、非法数据处理和消息幂等。

## 4. 持久化职责

- PostgreSQL 用于联系人及用户关系数据。
- MongoDB 用于消息记录持久化及消息查询。
- 存储访问通过应用层仓储接口；Handler 不拼接 SQL 或直接调用 MongoDB driver。
- 不得把消息记录重新写入 PostgreSQL，或把联系人/关系权威数据迁移到 MongoDB，除非用户明确批准架构变更。
- 数据迁移必须考虑索引、幂等、分页游标、失败恢复和向后兼容，并配有测试。
- Redis 仅按已确认用途使用，不替代 PostgreSQL 关系数据或 MongoDB 消息记录。

## 5. 健康与注册中心

- 注册中心健康报告默认周期为 600 秒（10 分钟），具体周期可配置。
- 健康报告使用独立后台任务、超时和有限重试；注册中心不可用不得阻塞连接建立、收发或 Handler。
- 不得自行假设注册中心产品、API、认证或租约协议；具体实现应遵从项目已确认的注册中心契约。
- 日志和健康状态中不得输出密码、token、连接 URI 凭据或私钥。

## 6. Rust 与项目约定

- 先检查工作区成员、crate 依赖、当前调用路径和测试命令；新增依赖前确认它与现有 Tokio/runtime、TLS 和 Rust toolchain 兼容。
- 优先沿用已有模块边界和异步风格；保持传输、业务、存储职责单一。
- 配置必须可验证并提供安全默认值；凭据从环境变量或安全配置注入，不提交真实秘密。
- 避免无关重构。用户提出的计划/文档任务不应顺带修改运行代码。
- 代码变更后运行相关测试和 `cargo check --workspace`；文档变更后检查文件头、路径、章节和链接/命令的一致性。
- 新行为应增加相应单元/集成测试；外部服务不可用时说明测试限制，不把编译通过描述为运行验证通过。

### 6.1 代码分隔与函数注释

- 源代码中不同逻辑代码块之间使用单独一行 `////////` 分隔；分隔行与前后代码块之间各空一行。文件头和函数文档注释属于例外，不在其内部插入分隔线。
- 每个需要文档注释的函数，注释第一行使用 `/// # [HANDLER] - 函数名称`，第二行使用 `/// * `DESC`: `函数间接``；将“函数名称”替换为实际函数名，将 DESC 的内容替换为该函数的简要说明。
- 即使函数不是网络 handler，也按统一格式使用 `[HANDLER]` 标签；不省略或调换两行顺序。

示例：

////////

```rust
/// # [HANDLER] - handle_message
/// * `DESC`: `校验并分发客户端消息`
async fn handle_message() {}
```

## 7. 计划与实现纪律

- `/PLAN` 中的计划记录目标、已确认约束、架构边界、分阶段验收、风险和待确认事项。
- 将“计划采用”“预留接口”“已实现”“已验证”明确区分，不把方案或 TODO 描述为已完成能力。
- 仅在用户当前模式允许时修改项目状态；计划模式只读分析，不改文件。
- 完成每项任务后核对实际修改文件及 Git 状态，并在回复中摘要说明验证结果和未解决事项。
